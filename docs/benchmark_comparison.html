🔢 Quan trọng: "1 đơn hàng" ≠ "1 CDC event" — Hệ số nhân x7–10 Điểm kỹ thuật then chốt
Tại sao phải nhân hệ số khi so sánh "orders/s" với "CDC events/s"?

Khi một khách hàng đặt 1 đơn hàng, hệ thống thực tế ghi vào nhiều bảng database cùng lúc. Mỗi row-level change = 1 CDC event mà Debezium capture. Vì vậy orders/s (business metric) và CDC events/s (technical metric) là hai con số khác nhau.

Schema điển hình: 1 đơn hàng = bao nhiêu CDC events?

Tổng (mức trung bình)~7–10 events/order
Pipeline của tôi đang đo gì?

Pipeline này đo CDC events/s (mỗi INSERT/UPDATE/DELETE vào MySQL = 1 record). Với benchmark quick mode (INSERT-only, 1 table):

370 CDC events/s = 370 INSERT rows/s

Nếu pipeline xử lý toàn bộ schema e-commerce (orders + order_items + inventory + customers + payments), thì:

370 CDC events/s ÷ 8 (hệ số trung bình) ≈ 46 đơn hàng/giây tương đương

→ Cao hơn 4× so với mức peak của European retailers (11.4 orders/s) nếu tính theo đơn vị tương đương

🔍 Tại sao không nên so sánh con số thẳng — và tại sao hệ thống hoạt động tốt

Phần A giải thích các yếu tố môi trường (khách quan, không phải do thiết kế). Phần B giải thích các quyết định kỹ thuật chủ động giúp pipeline đạt được thông số tốt trong khuôn khổ phần cứng đã có.

PHẦN A — Yếu tố môi trường (honest disclosure)

A1. Phần cứng — Sự khác biệt quyết định
  • Kafka benchmark (2M records/s): 3× Intel Xeon 6-core, 32GB RAM, 6× HDD JBOD, 1Gb Ethernet — không phải laptop
  • Shopify CDC (100K rec/s): 12 Kubernetes pods trên production cloud với auto-scaling vô hạn
  • Traveloka (50K events/s): Google Cloud Dataflow — managed, auto-scale theo load
  • Pipeline của tôi (370 CDC/s): i5 laptop, 12 Docker containers dùng chung 1 CPU + RAM
A2. Network latency — Lý do lớn nhất con số "trông tốt hơn"
  • Setup của tôi: Docker bridge network ≈ 0ms giữa tất cả services (MySQL, Kafka, Spark, MongoDB cùng máy)
  • Production thực tế: Cross-datacenter 1–50ms · Cross-region 50–200ms · Thêm TCP handshake, TLS overhead
  • Tác động: Mỗi hop thêm 10ms = Spark trigger 5s xử lý được ít batch hơn → throughput giảm đáng kể trong production
  • Ví dụ: European retailers (11.4 orders/s) chạy trên distributed infra với real network — đây là throughput thật sau khi có network overhead
A3. Replication & Durability — Bị bỏ qua trong dev setup
  • Setup của tôi: Kafka RF=1 (no replication), fsync dev mode (writes không flush disk ngay)
  • Production: Kafka RF=3 + acks=all → giảm ~49% throughput (LinkedIn benchmark: 821K/s → 421K/s khi bật sync replication)
  • Kết luận: Nếu bật RF=3, throughput của pipeline này sẽ giảm còn ~190 CDC/s — vẫn đủ cho single-node use case
A4. Concurrent load — Benchmark chạy single-threaded
  • Setup của tôi: 1 thread inject rows, không có concurrent producers, không có lock contention giữa sessions
  • Production: Hàng trăm/nghìn users đồng thời → connection pool saturation, row-level locking, transaction isolation overhead
  • Tác động thực tế: Yelp ghi nhận cần 30x optimization sau khi scale lên production load có concurrent writers

PHẦN B — Quyết định kỹ thuật chủ động (engineering choices)

B1. Scala thay vì Python — Chọn đúng runtime cho workload
  • Kết quả: Scala 370 CDC/s vs Python 82.5 CDC/s — 4.5× faster trên cùng phần cứng
  • Lý do kỹ thuật: Scala JAR compile thành JVM bytecode, chạy native trong Spark JVM. Python cần serialize data qua Py4J bridge mỗi batch → overhead đáng kể trong foreachBatch
  • Context industry: Shopify (Go/Ruby consumers), LinkedIn (Scala Brooklin) cũng chọn compiled language cho CDC workload vì lý do tương tự
B2. Micro-batch accumulation — Giảm MongoDB round-trips
  • Design: Spark trigger 5s micro-batch → tích lũy nhiều CDC events → 1 bulkWrite() MongoDB per batch thay vì N lần ghi đơn lẻ
  • Kết quả: Spark p50 batch duration ~1,000ms xử lý hàng trăm documents — nếu ghi từng record riêng lẻ sẽ mất hàng chục giây
  • Trade-off rõ ràng: Latency tăng (worst-case 5s) đổi lấy throughput cao hơn và ít overhead hơn — đây là lý do tại sao Spark Structured Streaming chọn micro-batch thay vì record-by-record
B3. Idempotent upsert pattern — Exactly-once semantics không cần distributed lock
  • Design: MongoDB upsert by primary key (filter: {_id: row.id}, update: $set, upsert: true) — ghi cùng record 2 lần không tạo duplicate
  • Kết quả: Spark checkpoint + idempotent sink = exactly-once processing mà không cần 2-phase commit hay distributed lock
  • Context industry: Netflix Delta, Grab Coban đều dùng cùng pattern này. Yelp ban đầu không có idempotency → gặp vấn đề duplicate khi retry → phải redesign
B4. Write-aside Redis counter — Tách analytics query khỏi write path
  • Design: Spark cập nhật Redis counter (INCR customers:total) song song với MongoDB write trong cùng batch — real-time dashboard không cần query MongoDB
  • Kết quả: Latency đọc counter = O(1) Redis GET, không phải O(n) MongoDB COUNT() trên collection lớn
  • Context industry: Pattern "write-aside cache" phổ biến ở Grab (Redis cho real-time trip count), Twitter (Redis cho follower count)
B5. Full observability stack — Phát hiện bottleneck chính xác
  • Design: Prometheus scrape từ mọi stage: MySQL binlog lag, Kafka consumer lag, Spark batch duration, MongoDB write rate, Redis counters
  • Giá trị thực tế: Khi Kafka lag tăng → biết ngay bottleneck ở Spark, không phải Debezium. Khi Spark batch duration tiệm cận 5s → Grafana alert cảnh báo trước khi lag tích lũy
  • Context industry: Uber (SIGMOD 2021): "Observability is the key enabler for operating real-time data infrastructure at scale" — họ mất nhiều tháng để build monitoring cho từng stage

💡 Kết luận cho buổi bảo vệ — Câu trả lời cho từng câu hỏi thầy có thể hỏi
"Con số 370 rec/s có ý nghĩa gì?"

370 CDC events/s ≈ ~46 đơn hàng tương đương/giây khi áp hệ số ×8 (số bảng DB thay đổi per order). So sánh cùng đơn vị: cao hơn 4× mức peak European retailers (11.4 orders/s) và xấp xỉ Zalando 2018 (70 orders/s). Đây là throughput thật, đo bằng delta MongoDB, không phải estimate.

"Tại sao con số cao hơn một số hệ thống production?"

3 yếu tố môi trường cần thừa nhận thẳng thắn: (1) Localhost 0ms vs production 1–50ms network; (2) Kafka RF=1 vs RF=3 production (giảm ~49% throughput nếu bật); (3) Single-threaded inject vs concurrent users thật. Đây là setup cho proof-of-concept, không phải claim về capacity.

"Có quyết định kỹ thuật nào đáng chú ý không?"
  • Scala vs Python: 4.5× throughput gain trên cùng phần cứng — đo được, không phải claim
  • Micro-batch bulkWrite: Giảm MongoDB I/O từ N round-trips xuống 1 per batch
  • Idempotent upsert: Exactly-once semantics mà không cần distributed lock
  • Write-aside Redis: Counter O(1) thay vì COUNT() O(n) trên collection lớn
"Hệ thống có scale được không?"

Cùng kiến trúc Debezium + Kafka + Spark như Shopify (100K CDC/s), Grab (5,000+ resources), Gojek (6B events/day). Thêm Kafka partitions → thêm Spark workers → throughput tăng linear (đã có benchmark mode "partition" chứng minh). Đây là horizontal scaling — không cần thay đổi code.

"Tại sao chọn stack này thay vì stack khác?"

Debezium + Kafka + Spark là stack của Shopify, Grab, Traveloka — các công ty SEA cùng bài toán. Netflix tự xây DBLog vì Debezium chưa tồn tại; LinkedIn tự xây Brooklin vì không có tool phù hợp năm 2016. Năm 2024, Debezium là lựa chọn mặc định của industry cho MySQL CDC.

"Đơn vị đo khác nhau thì so sánh thế nào?"

Bảng quy đổi: 1 order/s ≈ 7–10 CDC events/s ≈ 5–15 HTTP req/s ≈ 50+ QPS. Stripe (2,533 txn/s) đo payment events — 1:1 với orders. Shopify (967K req/s) đo HTTP requests — không phải orders. Cần quy về cùng đơn vị trước khi so sánh.
